# Taste
- Prefers to understand the root cause and see an approach/design before implementation, rather than jumping straight into code — when something is wrong he asks "why" and "how can we improve it" instead of just requesting a patch. Confidence: 0.65
- Strongly dislikes over-engineering and scope creep: build only exactly what was asked and keep solutions minimal (e.g. no pollers, persistence, alerting, or extra layers unless explicitly requested). Confidence: 0.85
- Prefers using free web search for data lookups instead of hammering paid/quota-limited APIs directly from scripts (e.g. explicitly asks to "search on web" and objects to burning the RailRadar API quota). Confidence: 0.6
- Values complete, comprehensive data over partial/hand-picked lists — objects when results are incomplete ("not getting every train") and wants full coverage across all cases (e.g. every train, all 7 days) so nothing is missed. Confidence: 0.6
- Likes the app to derive its output automatically from a single maintained data source (a Google Sheet / CSV he keeps) and surface the relevant slice for the current context (day/time), instead of requiring manual lookups. Confidence: 0.5
- Wants views/output kept concise and scannable: show only the immediately relevant items (e.g. the currently-live trains) grouped by status, rather than dumping the full list by default — long unfiltered lists prompt "you are giving me a lot of trains". Confidence: 0.55
- Prefers plain-language, non-technical summaries of what was built/changed — explicitly asks for explanations "in simple way" rather than dense technical detail. Repeatedly asks to be walked through the end-to-end "how does this actually work" data flow (e.g. "explain me our working... how we are getting updated live status") and responds well to simple diagrams/tables. Confidence: 0.75
- Does not accept "it's not a bug / it's the upstream's fault" as a stopping point — when he sees wrong-looking output in the running app he asks to *fix* it ("why is it showing 15 min rather than fixing"). Expect a real fix attempt in the same pass, with honest separation of which parts are ours and which are external. Confidence: 0.7
- Runs the app himself and pastes the exact rendered output back; expects changes to be verified against the real/live data before being reported done, not merely asserted. Confidence: 0.7
- Pastes raw rendered output and asks "explain me what does this mean" — wants a field-by-field decode of every column/label (including why a cell is `—`, what derived numbers like data age / polls / % to MTI / identified-by mean), delivered as a table with a one-line plain reading of the whole thing. He is the operator reading the app, not the code. Confidence: 0.6
- Wants these simple explanations formatted so he can relay them to a non-technical audience (his team) — asks for a "simple way so I explain working to my team", i.e. paste-ready, self-contained summaries with a one-line takeaway. Confidence: 0.6
- Stress-tests the design with concrete real-world scenarios instead of just reading the current output — e.g. "if the train is 68 min late it passes late; if the 10:55 train passes will our system detect that?". He reuses the assistant's own numbers as the scenario inputs, and expects the assumption to be *checked* (probe the live data / write a diagnostic) and, if it breaks, a guard plus a test — not a hypothetical answer. Confidence: 0.65
- Cross-checks the same field across two views (his live board screen vs the app's rendered table) and asks why they disagree — a mismatch between a live source and the app's displayed value is treated as a real defect to diagnose, not a cosmetic difference. Expect the answer to name which of the two sources is stale and why. Confidence: 0.55
- Treats API quota as a hard design constraint: proposed changes should be cost-neutral or cost-bounded, reusing data already fetched, and should be quantified in calls-per-event/per-minute when explained. Confidence: 0.55
- Wants explanations of the *dynamic list/pooling* behaviour spelled out, not just the trigger: how the live list is ranked, when an entry is dropped (e.g. once the train clears a checkpoint), and what refills the list to keep it full. He names the exact mechanism he wants covered ("are we doing ranking of pooling ... when the train passes Mitawali and remove it and add new"). Confidence: 0.6
- Writes terse, typo-heavy shorthand and expects the assistant to infer the real question and answer it directly, without asking for clarification or restating the request. Confidence: 0.5
- Needs *meeting-ready* artifacts, not just explanations: when he says "how should I explain it in meeting", he wants a pitch script — a one-line elevator pitch, per-section speaking lines, pre-written answers to the questions the stakeholder will likely ask ("if he asks how do we know which train?"), the one or two numbers worth memorising (e.g. API calls/min), and the open question to put to the boss for a decision. Flag known rough edges he might get caught on before he presents. He asks for a *fresh* meeting kit each time a feature is added or reworked (not a reference to the last one), and each must carry an explicit "weaknesses — raise these yourself" section, a list of questions to put to sir, and a step-by-step demo script. Confidence: 0.65
- Holds the simulation/demo path to real-world accuracy: the Simulate button's output is treated as a claim about what will actually happen, not as a decorative demo. When the row marked LIVE names a different train than the one that will genuinely pass next, he calls it out as "we are showing wrong train" — i.e. a demo that is convenient but unfaithful is a defect. Expect the identified train and the progress/percentage fields to be judged against the live board's actual ordering. Confidence: 0.6
- Treats data freshness/latency as a hard correctness requirement, not a cosmetic detail: he reports it in operational terms ("data updated is too late... it becomes too old and the train passes 2 stops"), so any position/progress/ETA shown must reflect where the train *is now*. A displayed freshness indicator that doesn't track real movement is worse than none. A source that is station-granular or minutes behind is not acceptable as the position authority; own hardware (sensors) or an authorized upstream beats a crowd-sourced third-party feed. He escalates this from "why is it stale" to "how do we fetch live data instead" — i.e. he wants a different *source*, not a faster poll loop. Confidence: 0.7
- When the current data source can't deliver what he needs, he asks "how can we fetch X" and expects a surveyed shortlist of alternative sources with an explicit recommendation and the trade-offs made visible (accuracy vs effort vs risk, including terms-of-service/legal viability) rather than just "poll the same endpoint more often". Confidence: 0.5
- Challenges a conclusion by asserting the domain truth he expects rather than posing an open question ("the correct train is X which will depart, but we are showing Y") — such a claim is to be verified against live data, and if it turns out to be wrong, for him to be told so directly, backed by the hard numbers (current station, route sequence index, stops remaining, times) that contradict him. Confidence: 0.55
- Uses the app's *own rendered numbers* as a correctness check: he compares a displayed percentage/progress field against what he can reason about ("93.7% to MTI" but the train is still 10 stops short of the origin station) and calls out that a high percentage implies imminent arrival when it isn't. A derived field that is technically true but semantically misleading counts as a bug — the field must mean what its label says. Confidence: 0.6
- Asks for the *logic/algorithm* to be restated and confirmed ("give me the logic we are using for the train rerank which will pass this is correct") so he can carry it into the meeting. When he pre-declares a subsystem correct, that is a green light to leave it alone — don't re-litigate it; spend the effort on the part he flagged as broken. Confidence: 0.55
- Builds an argument incrementally across turns and re-issues it once the assistant pushes back ("but we are showing wrong train in simulation as the correct train is varanasi which will depart") — he will hold the position through a full verification cycle, and expects the final answer to explicitly say whether he was right or wrong, with the timeline (departure times, current position) that settles it. Confidence: 0.55
- Repeats a question verbatim after an error/disconnect rather than rephrasing, and expects the assistant to resume from where it left off without re-explaining prior context. Confidence: 0.5
- When he needs to explain a subsystem to his team/boss, he wants the *verbatim code* — exact file path, real line numbers, and the actual guard clauses/conditions quoted with inline `# LINE nnn` markers — not a paraphrase of the logic. Fetch it with `grep -n` / `read_file` at the real offsets so he can paste precise references into the meeting. Pair it with a plain-words rule table (rule → line → why). Confidence: 0.65
- Asks a blunt "is our problem solved?" and expects an explicit per-item verdict up front (solved ✅ / not solved ❌ / not fixable in our code), with a clean split between what a code change can fix and what is an external/architectural limitation. He carries that verdict straight into the meeting, so a hedged or blended answer is useless to him. Confidence: 0.6
